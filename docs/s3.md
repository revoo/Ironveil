# S3 — Solo usability and offline delivery

## Status and scope

Implementation ready; **owner milestone playtest: awaiting playtest**. On November 5 the owner said the S2 systems were good and authorized continued development with refinement later. They also identified smoke camping and the repetitive Relay Control loop, and expressed a preference for team deathmatch. Those are unresolved design findings, not a passed claim that Relay is fun. This milestone delivers the scoped solo usability/offline work; team deathmatch is recorded as the preferred next mode experiment. No new mode, weapons, multiplayer infrastructure or movement retuning was added.

## Run

Development: `npm ci`, then `npm run dev`; open http://127.0.0.1:5173/. Settings and Guided training are in the header. The default game remains the local 2v2 Relay Control match.

Offline-ready build: `npm run build`, then `npm run preview`; open http://127.0.0.1:4173/. Wait for **Ready for offline solo** before closing the browser or disconnecting. Development mode does not register a service worker. Settings are local to each browser origin, so development and preview ports have separate saved settings. Cross-session match saves are not provided; reopening starts a new match.

## Difficulty and controls

Presets affect every bot equally and apply on the next restart/new match. Their HP, damage, vision, hull/turret rates and movement rules are identical to the human's.

| Preset | Reaction threshold | Effective decision-time reaction | Aim uncertainty | Historical sight memory |
| --- | --- | --- | --- | --- |
| Easy | 18 ticks / 0.6 s | about 0.667 s | ±0.15 rad | up to 45 ticks / 1.5 s |
| Normal | 9 ticks / 0.3 s | about 0.333 s | ±0.05 rad | up to 90 ticks / 3 s |
| Hard | 5 ticks / 0.167 s | about 0.167 s | ±0.025 rad | up to 90 ticks / 3 s |

Bot decisions remain staggered at 6 Hz. Evidence-investigation durations are 30/60/75 ticks for easy/normal/hard. Normal retains the prior effective reaction and aim baseline. These are starting parameters, not calibrated difficulty or guaranteed win-rate tiers.

Settings pause the match and clear input. Defaults remain WASD, Space fire, Shift quiet, Q smoke, right-click cancel, M mute and R restart. A remappable keyboard cancel action defaults to C. Escape opens Settings and pauses; closing the dialog leaves solo paused until Resume. All keyboard actions can be reassigned among supported keys. Conflicting bindings are rejected, including alternate Shift conflicts when the quiet action treats both Shift keys as equivalent. Form input cannot fire the cannon. Pausing, opening settings, changing bindings, blur and restart neutralize held input; key-repeat cannot bank a shot.

Effects volume, mute, text scale (100–150%), reduced motion, low effects, difficulty and bindings persist in local storage, with safe defaults if stored data is malformed or unavailable. Reduced motion removes cosmetic recoil and aim lead, and uses static impact rings. Low effects reduces transient effect capacity. Both preserve visibility, smoke lifetime/radius, historical tracks/markers, sound arcs, HP/charge facts and gameplay outcomes. Team symbols remain readable without color alone. The dialog has labels, keyboard focus styles and native Escape dismissal.

## Guided training and presentation

Guided training is an optional nine-exercise sequence with restart and skip/return controls: drive/turn; deliberate independent aim; tap fire; charge/cancel; mud tracks; brush; quiet approach; smoke escape; relay scoring. It uses local authored fixtures with bots disabled and the same simulation rules. The authority sets lesson positions; client transforms are never accepted. Progress uses the player's authorized state/evidence. Tap training requires actual target damage, not merely a fired shell; charge training requires cancellation plus a sufficiently charged shot and target damage. Merely waiting does not complete exercises.

The layout fits the logical 960 × 540 playfield into the available training viewport. The HUD displays current bindings and can scale without adding world-view area. A visual check confirmed the training card and playfield readability. A regression exposed stale pointer projection after a DOM layout change moved the canvas: the barrel could settle about 0.19 radians away from the intended cursor direction. Current canvas bounds and raw screen cursor position now feed Phaser's coordinate transforms each frame. The same test fails before the fix and passes after it. This preserves the approved movement physics while fixing aim/layout consistency.

A full browser walkthrough completed all nine actual exercises. This does not establish that an unfamiliar human learns them in three minutes; the original multi-person tutorial/readability gate remains unperformed. Placeholder geometry and procedural sounds are retained while mode/encounter design is still being refined. No final art or audio-quality claim is made.

Worker errors, malformed message failures or a communication stall show a visible reload action instead of an unexplained frozen match. The failed authority is terminated; reloading starts a fresh game. A delayed-start regression caught Settings opening before the Worker match existed; pause intent now survives initialization and lesson setup.

## Offline architecture

The build writes `dist/sw.js` after Vite emits the full application. Its version hashes the production manifest and service-worker template. The manifest hashes all emitted runtime assets; currently the four shell assets are index HTML, main JS, CSS and Worker JS. Maps, tuning, settings code, procedural graphics and sound synthesis are inside those bundles; no remote fonts or media are required.

Installation downloads and SHA-256 verifies the entire version before publishing it. Responses are written to a unique candidate cache, then one metadata pointer commit makes that complete cache visible. A failed download, hash mismatch or storage write deletes the candidate and leaves the installed version's pointer intact. Repair uses the same complete-candidate process. Readiness checks every required cached asset; missing content produces a restore prompt rather than claiming offline support.

Only same-origin manifest assets and the root/index navigation are handled. Non-GET traffic, multiplayer/API/room/health paths and unrelated requests are not cached as offline responses. No reconnect tokens or API response data are stored. Offline requires a successful initial load/cache; a new uncached offline browser cannot load the app. Browser storage eviction can require a connection to restore content; if the shell itself is gone, a fresh online load is required.

A new service worker installs in the background but does not call skipWaiting. It waits for the old version's tabs to close, preserving open matches and assets. Settings offers an update notice at that menu boundary: finish the match, close all Ironveil tabs and reopen. Obsolete shell caches are removed on activation. This follows the documented [service-worker lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers.). The application does not force a mid-match reload.

## Verification and TDD

Local results: **83 unit tests, 23 browser acceptance tests, map/route validation and production build pass**. Unit tests were written before settings parsing/input remapping, difficulty differences, tutorial progress and offline install/readiness behavior. Red checks showed missing behavior before implementation; fixes were followed by green checks. Follow-up regressions covered alternate Shift conflicts, missed shots prematurely advancing training, startup pause ordering and cursor projection after layout changes.

The cache tests exercise interrupted installs, mismatched hashes, retention of an installed version and missing-asset detection. Production browser checks perform an actual Chromium process shutdown and a new process launch with network access disabled, then verify cached boot, rendering, audio unlock and driving input. Separate checks delete a cached Worker asset, detect the missing content and restore it online; an uncached first offline visit fails as expected. These are real production-preview tests, not just a disconnected running tab. A controlled Worker failure fixture verifies the visible recovery UI; real Worker simulation/replay tests remain in the suite.

The complete tutorial uses real controls, cancel/recovery and charge-state checks, and confirmed target damage. An initial parallel run failed that exercise. Investigation found both fragile wall-clock waits and the actual stale-canvas pointer defect; the test now waits for simulation state, retains hit requirements and passes with the projection fix. Existing movement, stealth, score/lifecycle and training-range regression checks remain intact.

Headless diagnostics ran 100 seeds per preset with an idle human (300 matches total). All matches terminated; all Red wins reflect the idle player and are not difficulty calibration:

| Preset | Deaths | Maximum active shells | Longest measured bot stop away from the relay |
| --- | ---: | ---: | ---: |
| Easy | 1,648 | 5 | 1.07 s |
| Normal | 1,785 | 5 | 2.23 s |
| Hard | 1,809 | 4 | 11.17 s |

The hard-preset linger is a known AI refinement item, not evidence of optimal tactics or a fairness result. No indefinite stuck state was observed in those runs; this is not exhaustive navigation proof.

No GitHub CI run was triggered. The manual workflow can validate this substantial checkpoint after owner review. Its existing build output is reused by the production-preview tests in CI to avoid building twice. Locally, browser tests build preview assets and start dev, the legacy diagnostic server and production preview as separate managed processes.
